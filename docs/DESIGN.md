## 1. システム構成

自分でサーバーを用意・管理しなくて済む構成にしています。

```text
   スマホA          スマホB          スマホC
  ┌────────┐      ┌────────┐      ┌────────┐
  │ブラウザ │      │ブラウザ │      │ブラウザ │
  └───┬────┘      └───┬────┘      └───┬────┘
      │ ①画面のファイルを読み込む（最初の1回）
      ▼
  ┌──────────────────────────┐
  │ GitHub Pages             │  index.html / css / js / data
  │（ファイルを配るだけ）       │
  └──────────────────────────┘

      │ ②ゲーム中のデータをやり取りする（つながりっぱなし）
      ▼
  ┌──────────────────────────────────────────┐
  │ Firebase                                 │
  │  ・Authentication（匿名認証）… 端末ごとのID │
  │  ・Realtime Database … ルーム・点数・選択   │
  └──────────────────────────────────────────┘
```

- **GitHub Pages** は、HTML・CSS・JavaScript のファイルを配るだけです。
- **Firebase** が、ルーム管理・ゲーム状態の保存・全員への同期を受け持ちます。
- ゲームのルールの計算は、**各プレイヤーのブラウザ**で行います（専用のサーバープログラムはありません）。

## 2. 使用技術と、選んだ理由

| 使うもの | 理由 |
|---|---|
| HTML / CSS / JavaScript（そのまま） | ビルド（変換作業）が不要。ファイルを置くだけで動き、書き換えてすぐ確認できる |
| ES Modules（`import` / `export`） | ファイルを役割ごとに分けられる |
| Firebase Realtime Database | 無料枠で足りる。データが変わると全端末に自動で届く。スマホの回線でも安定してつながる |
| Firebase 匿名認証 | 登録なしで端末ごとのIDがもらえる。リロードしても同じ人として扱える |
| GitHub Pages | 無料で公開できる。ファイルをアップロードするだけ |
| Python（変換スクリプトのみ） | Excel → JSON の変換。追加ライブラリなしで動く |

**ほかの候補を選ばなかった理由**

- **Supabase**：無料プランは一定期間使わないとプロジェクトが停止する。たまに遊ぶ用途には向かない。
- **自前の WebSocket サーバー**（Render など）：サーバーの管理が必要。無料枠はしばらく使わないと停止し、起動に時間がかかる。
- **WebRTC（端末同士の直接通信）**：サーバー不要だが、携帯回線ではつながらないことがある。

## 3. データ構造

### 3-1. キャラクターデータ（`data/characters.json`）

Excelから「順位」と「名前」だけを取り出したものです。

```json
[
  {"id": 1, "rank": 1, "name": "古明地 こいし", "yomi": "こめいじ こいし"},
  {"id": 2, "rank": 2, "name": "霧雨 魔理沙", "yomi": "きりさめ まりさ"},
  {"id": 4, "rank": 4, "name": "フランドール・スカーレット"}
]
```

| 項目 | 意味 |
|---|---|
| `id` | キャラクターを区別する通し番号。**「同じキャラを選んだか」の判定に使う** |
| `rank` | 人気投票の順位。**加算する点数** |
| `name` | 表示する名前 |
| `yomi` | 検索用のよみがな（漢字を含む名前だけ。`tools/yomi.json` から入る） |

> **なぜ `id` が必要？**
> 第22回の結果には同率順位があります（195位が2人、197位が3人 など9組）。
> 順位だけで比べると、別のキャラなのに「重複」と判定されてしまうため、`id` で区別しています。

### 3-2. Firebase Realtime Database の中身

```text
rooms/
  {ルームID}/                     例: A7K3P
    hostUid: "…"                  ルームを作った人のID
    createdAt: 1790000000000      作成日時
    players/
      {uid}/                      ルームにいる人（待機画面の名簿）
        name: "しょうた"
        joinedAt: 1790000000000   入室した時刻（並び順に使う）
        online: true              つながっているか
    state/                        ★ゲームの状態（4章で説明）
      status: "playing"
      gameNo: 1
      turn: 3
      phase: "select"
      scores/
        {uid}: { name: "しょうた", order: 0, total: 87, out: false }
      banned/
        c3: 1                     キャラid 3 は、1ターン目に使用禁止になった
      history/
        t1/
          {uid}: { charId: 3, outcome: "duplicate", gained: 0, before: 0, after: 0, out: false }
    submitted/
      g1t3/                       1ゲーム目・3ターン目
        {uid}: true               「決定した」という印（誰を選んだかは入っていない）

picks/
  {ルームID}/
    g1t3/
      {uid}: 37                   ★秘密★ 選んだキャラのid
```

**ポイント：「誰を選んだか」(`picks`) だけを別の場所に置いている**

`rooms/{ルームID}` 以下は、ルームIDを知っている人なら読めます。
`picks` はセキュリティルールで「自分が決定した後でないと読めない」ようにしてあります。
読める人を別々に決めるために、置き場所を分けています。

**キーに `c3` `t1` `g1t3` のような文字をつけている理由**

Firebase は、キーが `1, 2, 3 …` と数字だけで並んでいると、勝手に「配列」として扱うことがあります。
そうなるとプログラムが複雑になるので、頭に文字をつけて必ず「オブジェクト」になるようにしています。

## 4. ゲーム状態の管理方法

### 4-1. 状態は1か所（`rooms/{ルームID}/state`）にまとめる

各プレイヤーの画面は、この `state` を見て描かれます。
「自分の端末だけが知っている点数」のようなものは持ちません。
そのため、**リロードしても、通信が切れてつなぎ直しても、同じ画面に戻れます。**

### 4-2. 状態の移り変わり

```text
 status: lobby ──[ホストがゲーム開始]──▶ status: playing
（待機画面）                                   │
                                              ▼
                              ┌──▶ phase: select（キャラクター選択）
                              │        │ 全員が決定
                              │        ▼
                              │    phase: reveal（結果公開）
                              │        │ ホストが「次へ」
                              │        ├── まだ続く ──┐
                              └────────────────────┘
                                       │ 5ターン目が終わった／全員OUT
                                       ▼
                                 status: finished（最終結果）
                                       │ ホストが「もう一度」
                                       ▼
                                 status: lobby
```

### 4-3. ルールの計算は「純粋な関数」に分ける

`js/game-logic.js` の関数は、**状態を受け取って、新しい状態を返すだけ**です。画面にも通信にも触りません。

```text
resolveTurn( 今の状態, 全員の選択, キャラクター表 ) → 結果を反映した新しい状態
advance( 今の状態 )                               → 次のターン（または終了）の状態
judgeResult( 最後の状態 )                          → 勝者と順位
```

こうしておくと、ルールを変えたいときに見る場所が1つで済み、`tests/` で正しさを確認できます。

### 4-4. 状態の書き換えは「トランザクション」で行う

5人の端末が同時に「結果を計算しよう」とすると、二重に加点されてしまうおそれがあります。
そこで、状態の書き換えは必ず次の形で行います（`room.js`）。

```js
backend.updateState(roomId, (state) => {
  // まだ「選択フェーズ」のときだけ計算する
  if (state.phase !== 'select') return undefined;   // もう誰かが計算済み → 何もしない
  return resolveTurnLogic(state, picks, charById);
});
```

Firebase のトランザクションは、「読んでから書くまでの間に他の人が書き換えていたら、最新の値でやり直す」しくみです。
やり直したときには `phase` がもう `reveal` になっているので、2人目以降は何もせずに終わります。

## 5. 画面構成

すべての画面は `index.html` に入っていて、`showScreen('lobby')` のように切り替えます（1つだけ表示）。

| # | 画面 | id | 表示される条件 |
|---|---|---|---|
| 1 | トップ | `screen-top` | ルームに入っていないとき |
| 2 | ルーム作成 | `screen-create` | 「ルームを作成」を押したとき |
| 3 | ルーム参加 | `screen-join` | 「ルームに参加」を押したとき／招待リンクで開いたとき |
| 4 | 待機 | `screen-lobby` | `status` が `lobby` |
| 5 | ゲーム | `screen-game` | `status` が `playing`、`phase` が `select` |
| 6 | ターン結果 | `screen-reveal` | `status` が `playing`、`phase` が `reveal` |
| 7 | 最終結果 | `screen-result` | `status` が `finished` |

ゲーム画面（5）は、自分の状況で中身が変わります。

| 自分の状況 | 表示 |
|---|---|
| まだ決定していない | 検索欄＋キャラクター一覧＋下の決定欄 |
| 決定した | 「あなたの選択」と、ほかの人を待つ表示 |
| OUTになった | 観戦の表示 |

画面上部のステータスバー（ターン・残りターン・目標値・自分の合計点）は、スクロールしても常に見えます。

## 6. リアルタイム通信の方法

### 6-1. 全員が同じ場所を「購読」する

ルームに入ると、`rooms/{ルームID}` の変化を受け取り続けます（`watchRoom`）。
誰かがデータを書き換えると、全員の端末で `onRoomChange` が呼ばれ、画面が描き直されます。

```text
  誰かが書き込む ─▶ Firebase ─▶ 全員の onRoomChange(room) ─▶ render()
```

「メッセージを送り合う」のではなく、「同じデータを全員で見ている」と考えると分かりやすいです。

### 6-2. 1ターンの流れ（同時公開のしくみ）

```text
  Aさん                Firebase                 Bさん
   │ キャラを選んで決定                          │
   │── picks/…/A = 37（秘密）──▶│                │
   │── submitted/…/A = true ──▶│── Aが決定した ─▶│ 「A：決定」と表示
   │                           │                │ （誰を選んだかは届かない）
   │                           │                │ キャラを選んで決定
   │                           │◀── picks/…/B = 12（秘密）
   │◀── Bが決定した ───────────│◀── submitted/…/B = true
   │                           │                │
   │  全員が決定したと分かる      │                │  全員が決定したと分かる
   │── 全員の picks を読む ────▶│◀──── 全員の picks を読む
   │── 結果を計算して state を更新（トランザクション）
   │                           │   ※先に届いた1回だけが反映される
   │◀── state: phase = reveal ─│── state: phase = reveal ─▶│
   │  結果公開の画面へ           │                │  結果公開の画面へ
```

**相手の選択を見てから選べない理由**

セキュリティルール（`database.rules.json`）で、`picks` を次のように守っています。

- 書けるのは自分の欄に **1回だけ**（書いたら変更できない）
- そのラウンドの全員分を読めるのは、**自分の選択を書いた後**（またはOUTの人）だけ

つまり「先に自分の選択を確定させないと、ほかの人の選択は読めない」ので、後出しはできません。

**結果を計算するのは誰？**

「自分の選択を送り終えた人」の端末が、全員そろったことに気づいた時点で計算します。
たいていは最後に決定した人の端末です。ホストの端末に頼らないので、
ホストのスマホがスリープしていても結果公開まで進みます。

### 6-3. 切断の検知（プレゼンス）

`players/{uid}/online` で、つながっているかを表します。
Firebase の `onDisconnect` という機能で、「接続が切れたら、サーバー側で `false` と書く」よう予約しています。
ブラウザを閉じても、電波が切れても、サーバーが気づいて `false` にしてくれます。

## 8. 各ファイルの説明

呼び出しの関係は、上から下への一方向です。

```text
  main.js          入口。ボタンの処理、画面の切り替え
    ├─ views.js        画面を描く
    ├─ room.js         ルームとゲームの操作
    │    ├─ game-logic.js   ルールの計算
    │    └─ backend.js      通信係を選ぶ
    │          ├─ backend-firebase.js
    │          └─ backend-local.js
    ├─ util.js         小さな道具
    └─ config.js       設定値
```

### `js/config.js` ― 設定値

目標値 150、ターン数 5、人数 2〜5 などの数字を1か所にまとめています。
ルールの数字を変えたいときは、ここだけ書き換えます。

### `js/game-logic.js` ― ルールの計算

**このゲームで一番大事なファイルです。** 画面にも通信にも触らない、計算だけの関数が入っています。

| 関数 | すること |
|---|---|
| `createGameState(参加者, ゲーム番号)` | 全員0点・1ターン目の状態を作る |
| `resolveTurn(状態, 全員の選択, キャラ表)` | 1ターン分の計算（下で説明） |
| `advance(状態)` | 次のターンへ進める。5ターン目の後、または全員OUTなら終了 |
| `judgeResult(状態)` | 勝者と順位を決める |
| `allActiveSubmitted(状態, 決定済みの印)` | OUTでない人が全員決定したか |

`resolveTurn` の中身は、仕様の「重要なゲームロジック」と同じ順番です。

1. OUTでない人の「有効な選択」を集める（未選択・使用禁止キャラは除く）
2. キャラクターごとに、選んだ人数を数える
3. 1人ずつ結果を決める
   - 2人以上が選んだキャラ → **+0**、そのキャラを使用禁止リストに追加
   - それ以外 → **順位を加点**
   - 合計が 150 を超えたら **OUT**（`after > TARGET_SCORE`。ちょうど150はセーフ）

結果の種類（`outcome`）は4つです。

| `outcome` | 意味 | 加点 |
|---|---|---|
| `ok` | ふつうに選んだ | 順位 |
| `duplicate` | ほかの人と重複した | 0 |
| `none` | 選ばなかった（ホストに締め切られた） | 0 |
| `invalid` | 使用禁止のキャラだった（画面では選べないが、念のため） | 0 |

### `js/room.js` ― ルームとゲーム進行の操作

「ルームを作る」「参加する」「開始する」「決定する」「結果を計算する」「次へ進む」をまとめています。
それぞれ、**条件を確かめる → 通信係に頼む** という形です。

- 失敗したときは `GameError` を投げます。メッセージはそのまま画面に出せる日本語です。
  （例：「このルームはすでにゲームが始まっています。途中参加はできません。」）
- `hostUidOf(room)`：いまホストとして操作できる人を返します。
  ルームを作った人が切断しているあいだは、オンラインの人のうち最初に入室した人が代わりになります。
- `resolveTurn` / `goNext` / `backToLobby`：4-4 のトランザクションで状態を書き換えます。

### `js/backend.js` と2つの通信係

`backend-firebase.js`（本番用）と `backend-local.js`（お試し用）は、**同じ名前・同じ動きの関数**を持っています。
`backend.js` が、`firebase-config.js` に設定があるかどうかを見て、どちらを使うか決めます。

| 関数 | すること |
|---|---|
| `init()` | 準備をして、自分のID(uid)を返す |
| `watchRoom(roomId, onChange)` | ルームの変化を受け取り続ける |
| `createRoom` / `writeMyPlayer` | ルームを作る／自分を名簿に書く・消す |
| `startPresence` / `stopPresence` | オンライン表示を始める／やめる |
| `updateState(roomId, updater)` | ゲーム状態を安全に書き換える（トランザクション） |
| `submitPick` | 自分の選択を送る（秘密の選択と、公開の「決定した印」を同時に書く） |
| `readPicks` / `readMyPick` | 全員の選択を読む／自分の選択を読む |

**通信係を分けている利点**

- Firebase を設定する前でも、1台のPCで全部の画面を試せる。
- ゲーム側のコード（`room.js` など）は、通信のしくみを知らなくてよい。
- 将来、別のサービスに乗り換えるときは、同じ関数を持つファイルをもう1つ作ればよい。

`backend-local.js` は、Firebase のセキュリティルールと同じ制限（開始後は参加できない、
決定前はほかの人の選択を読めない、など）をプログラムで再現しています。

### `js/views.js` ― 画面の描画

`app`（アプリの状態）を受け取って、`index.html` の中身を書き換えます。ボタンの処理は入っていません。

- 画面ごとに `renderLobby` / `renderGame` / `renderRevealCards` / `renderResult` があります。
- プレイヤー名など、利用者が入力した文字は必ず `escapeHtml()` を通してからHTMLに入れています。
  （名前に `<script>` のような文字を入れられても、画面が壊れないようにするため）
- `searchCharacters`：検索のしくみです。数字だけなら順位、それ以外は名前とよみがなで探します。

### `js/main.js` ― アプリの入口

1. **起動**：キャラクターデータを読み、通信係を準備する
2. **入室**：ルームを作る／参加する。リロード後は、保存しておいたルームIDで元のルームに戻る
3. **同期**：ルームのデータが変わるたびに `render()` で画面を描き直す
4. **操作**：ボタンが押されたら `room.js` の操作を呼ぶ
5. **自動処理**（`autoActions`）：全員が決定したら結果を計算する

`render()` は、状態を見てどの画面を出すかを決めるだけです。

```js
if (state.status === 'lobby')    → 待機画面
if (state.status === 'finished') → 最終結果画面
if (state.phase === 'reveal')    → ターン結果画面
それ以外                          → ゲーム画面
```

キャラクター一覧と結果公開のカードは、**新しいターンに入ったときだけ**作り直しています。
データが届くたびに作り直すと、検索中の文字やスクロール位置が消えたり、演出がやり直しになったりするためです。

### `js/util.js` ― 小さな道具

`$('id')`（要素を取り出す）、`showScreen`（画面切り替え）、`showToast`（下に出るメッセージ）、
`confirmDialog`（確認ダイアログ）、`normalizeText`（検索用に文字をそろえる）などです。

### `index.html` / `css/style.css`

- `index.html`：7つの画面の骨組みが全部入っています。中身（名前や点数）は `views.js` が入れます。
- `style.css`：スマホの縦画面を基本にしています。先頭の `:root` で色をまとめて管理しています。
  キャラクターの画像は使わず、陰陽玉のマークも図形（SVG）で描いています。

### `tools/convert_excel.py`

Excel（`.xlsx`）を読み、`data/characters.json` を作ります。
`.xlsx` は「XMLファイルをZIPでまとめたもの」なので、Python に最初から入っている機能だけで読めます。
読むのは「順位」と「名前」の列だけです。

### `database.rules.json`

Firebase のセキュリティルールです。各行に説明を書いてあります。守っていることは次の5つです。

1. ログイン（匿名認証）していない人は、何も読み書きできない
2. ルームの一覧は誰も見られない（ルームIDを知っている人だけが、そのルームを読める）
3. ゲーム開始後は、新しく参加できない
4. 選択は自分の分を1回だけ書ける
5. ほかの人の選択は、自分が決定した後でないと読めない

## 9. エラーや切断への対応

| 起きること | どうなるか | 関係する場所 |
|---|---|---|
| 通信が途中で切れた | 上に「通信が切れています」と出る。つながり直すと自動で続きから。ほかの人には「切断中」と表示される | `main.js` `watchConnection`、`backend-firebase.js` `startPresence` |
| ブラウザをリロードした | 保存しておいたルームIDで、同じゲームの同じ画面に戻る。決定済みの選択も読み直す | `main.js` `openFirstScreen` `restoreMyPick` |
| 存在しないルームIDを入力した | 「そのルームIDのルームは見つかりません」 | `room.js` `joinRoom` |
| すでに始まっているルームに入ろうとした | 「途中参加はできません」。ルールでも書き込みを拒否する | `room.js` `joinRoom`、`database.rules.json` |
| 満員のルームに入ろうとした | 「このルームは満員です」 | `room.js` `joinRoom` |
| キャラを選ばずに決定を押した | 「先に、一覧からキャラクターを選んでください」 | `main.js` `onDecide` |
| 使用禁止のキャラを選ぼうとした | 一覧で灰色になり、押しても選べない。万一送られても加点しない | `main.js` `onCharTap`、`game-logic.js` `resolveTurn` |
| OUTの人が操作しようとした | キャラクター一覧が出ない（観戦表示）。ルールでも書き込みを拒否する | `views.js` `renderGame`、`database.rules.json` |
| 誰かがなかなか選ばない・戻ってこない | ホストは「未選択の人を待たずに結果を公開」で進められる（その人は +0） | `main.js` `onForce` |
| ホストが切断した | オンラインの人のうち、最初に入室した人がホストの操作をできる | `room.js` `hostUidOf` |
| 2人が同時に同じ操作をした | トランザクションにより、1回だけ反映される | `room.js`、4-4 |

## 10. 機能を足すときのヒント

| やりたいこと | 手を入れる場所 |
|---|---|
| 制限時間をつける | `state` に締め切り時刻を入れ、`main.js` の `autoActions` で時間切れなら `resolveTurn` を呼ぶ |
| 「パス（何も選ばない）」を追加する | `game-logic.js` の `resolveTurn` に `outcome: 'pass'` を足し、`views.js` にボタンを足す |
| 自分が一度選んだキャラを選べなくする | `state` に各自の使用済みリストを足し、`resolveTurn` と `renderCharList` で使う |
| キャラクターの画像を出す | `characters.json` に画像のパスを足し、`views.js` の `renderCharList` で表示する（権利に注意） |
| 効果音をつける | `main.js` の `render()` で、画面が切り替わるときに鳴らす |
| 人数を増やす | `config.js` の `MAX_PLAYERS` を変える |

ルールを変えたときは、`tests/game-logic.test.js` にテストを足しておくと、後で安心して直せます。
