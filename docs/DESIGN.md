## 1. システム構成

自分でサーバーを用意・管理しなくて済む構成にしています。

```text
   スマホA          スマホB          スマホC
  ┌────────┐      ┌────────┐      ┌────────┐
  │ブラウザ │      │ブラウザ │      │ブラウザ │
  └───┬────┘      └───┬────┘      └───┬────┘
      │ ①画面のファイルを読み込む（最初の1回）
      ▼
  ┌──────────────────────────┐
  │ GitHub Pages             │  index.html / css / js / data
  │（ファイルを配るだけ）       │
  └──────────────────────────┘

      │ ②ゲーム中のデータをやり取りする（つながりっぱなし）
      ▼
  ┌──────────────────────────────────────────┐
  │ Firebase                                 │
  │  ・Authentication（匿名認証）… 端末ごとのID │
  │  ・Realtime Database … ルーム・点数・選択   │
  └──────────────────────────────────────────┘
```

- **GitHub Pages** は、HTML・CSS・JavaScript のファイルを配るだけです。
- **Firebase** が、ルーム管理・ゲーム状態の保存・全員への同期を受け持ちます。
- ゲームのルールの計算は、**各プレイヤーのブラウザ**で行います（専用のサーバープログラムはありません）。

## 2. 使用技術と、選んだ理由

| 使うもの | 理由 |
|---|---|
| HTML / CSS / JavaScript（そのまま） | ビルド（変換作業）が不要。ファイルを置くだけで動き、書き換えてすぐ確認できる |
| ES Modules（`import` / `export`） | ファイルを役割ごとに分けられる |
| Firebase Realtime Database | 無料枠で足りる。データが変わると全端末に自動で届く。スマホの回線でも安定してつながる |
| Firebase 匿名認証 | 登録なしで端末ごとのIDがもらえる。リロードしても同じ人として扱える |
| GitHub Pages | 無料で公開できる。ファイルをアップロードするだけ |
| Python（変換スクリプトのみ） | Excel → JSON の変換。追加ライブラリなしで動く |

**ほかの候補を選ばなかった理由**

- **Supabase**：無料プランは一定期間使わないとプロジェクトが停止する。たまに遊ぶ用途には向かない。
- **自前の WebSocket サーバー**（Render など）：サーバーの管理が必要。無料枠はしばらく使わないと停止し、起動に時間がかかる。
- **WebRTC（端末同士の直接通信）**：サーバー不要だが、携帯回線ではつながらないことがある。

## 3. データ構造

### 3-1. キャラクターデータ（`data/characters.json`）

Excelから「順位」と「名前」だけを取り出したものです。

```json
[
  {"id": 1, "rank": 1, "name": "古明地 こいし", "yomi": "こめいじ こいし"},
  {"id": 2, "rank": 2, "name": "霧雨 魔理沙", "yomi": "きりさめ まりさ"},
  {"id": 4, "rank": 4, "name": "フランドール・スカーレット"}
]
```

| 項目 | 意味 |
|---|---|
| `id` | キャラクターを区別する通し番号。**「同じキャラを選んだか」の判定に使う** |
| `rank` | 人気投票の順位。**加算する点数**（画面に出すのは結果公開の後だけ） |
| `name` | 表示する名前 |
| `yomi` | よみがな。検索と、一覧の50音順の並びに使う（漢字を含む名前だけ。`tools/yomi.json` から入る） |

ファイルの中は順位順に並んでいますが、画面の一覧は50音順です。
読み込んだときに `util.js` の `prepareCharacters` が並べ替えます（順位順のままだと、並びから順位が分かってしまうため）。

> **なぜ `id` が必要？**
> 第22回の結果には同率順位があります（195位が2人、197位が3人 など9組）。
> 順位だけで比べると、別のキャラなのに「重複」と判定されてしまうため、`id` で区別しています。

### 3-2. Firebase Realtime Database の中身

```text
rooms/
  {ルームID}/                     例: A7K3P
    hostUid: "…"                  ルームを作った人のID
    createdAt: 1790000000000      作成日時
    players/
      {uid}/                      ルームにいる人（待機画面の名簿）
        name: "霊夢"
        joinedAt: 1790000000000   入室した時刻（並び順に使う）
        online: true              つながっているか
    state/                        ★ゲームの状態（4章で説明）
      status: "playing"
      gameNo: 1
      mode: "normal"              ゲームモード（11章で説明）
      rules/                      そのモードのルール。全員がこの値を見るので、ルールは全員同じになる
        targetScore: 50           目標値
        burstScore: 51            バーストする点数（合計がこの点数以上でバースト）
        maxTurns: 5               ターン数
        minRank: 1                使えるキャラクターの順位（開始）
        maxRank: 50               使えるキャラクターの順位（終了）。無ければ「最後の順位まで」
      original/                   ホストが決めたオリジナルのルール（決めたときだけ。形は rules と同じ）
      difficulty: "reload"        前のバージョンの画面を止めるための印（11-4 で説明。いまのコードは読まない）
      turn: 3
      phase: "select"
      scores/
        {uid}: { name: "霊夢", order: 0, total: 87, out: false }   out は「バーストしたか」
      banned/
        c3: 1                     キャラid 3 は、1ターン目に使用禁止になった
      history/
        t1/
          {uid}: { charId: 3, outcome: "duplicate", gained: 0, before: 0, after: 0, out: false }
    submitted/
      g1t3/                       1ゲーム目・3ターン目
        {uid}: true               「決定した」という印（誰を選んだかは入っていない）

picks/
  {ルームID}/
    g1t3/
      {uid}: 37                   ★秘密★ 選んだキャラのid
```

**ポイント：「誰を選んだか」(`picks`) だけを別の場所に置いている**

`rooms/{ルームID}` 以下は、ルームIDを知っている人なら読めます。
`picks` はセキュリティルールで「自分が決定した後でないと読めない」ようにしてあります。
読める人を別々に決めるために、置き場所を分けています。

**キーに `c3` `t1` `g1t3` のような文字をつけている理由**

Firebase は、キーが `1, 2, 3 …` と数字だけで並んでいると、勝手に「配列」として扱うことがあります。
そうなるとプログラムが複雑になるので、頭に文字をつけて必ず「オブジェクト」になるようにしています。

## 4. ゲーム状態の管理方法

### 4-1. 状態は1か所（`rooms/{ルームID}/state`）にまとめる

各プレイヤーの画面は、この `state` を見て描かれます。
「自分の端末だけが知っている点数」のようなものは持ちません。
そのため、**リロードしても、通信が切れてつなぎ直しても、同じ画面に戻れます。**

### 4-2. 状態の移り変わり

```text
 status: lobby ──[ホストがゲーム開始]──▶ status: playing
（待機画面。ホストが                           │   ※ここでモードとルールが固定される
  モードを選ぶ）                               ▼
                              ┌──▶ phase: select（キャラクター選択）
                              │        │ 全員が決定
                              │        ▼
                              │    phase: reveal（結果公開）
                              │        │ ホストが「次へ」
                              │        ├── まだ続く ──┐
                              └────────────────────┘
                                       │ 最後のターンが終わった／全員バースト
                                       ▼
                                 status: finished（最終結果）
                                       │ ホストが「もう一度」
                                       ▼
                                 status: lobby
```

### 4-3. ルールの計算は「純粋な関数」に分ける

`js/game-logic.js` の関数は、**状態を受け取って、新しい状態を返すだけ**です。画面にも通信にも触りません。

```text
resolveTurn( 今の状態, 全員の選択, キャラクター表 ) → 結果を反映した新しい状態
advance( 今の状態 )                               → 次のターン（または終了）の状態
judgeResult( 最後の状態 )                          → 勝者と順位
```

こうしておくと、ルールを変えたいときに見る場所が1つで済み、`tests/` で正しさを確認できます。

### 4-4. 状態の書き換えは「トランザクション」で行う

5人の端末が同時に「結果を計算しよう」とすると、二重に加点されてしまうおそれがあります。
そこで、状態の書き換えは必ず次の形で行います（`room.js`）。

```js
backend.updateState(roomId, (state) => {
  // まだ「選択フェーズ」のときだけ計算する
  if (state.phase !== 'select') return undefined;   // もう誰かが計算済み → 何もしない
  return resolveTurnLogic(state, picks, charById);
});
```

Firebase のトランザクションは、「読んでから書くまでの間に他の人が書き換えていたら、最新の値でやり直す」しくみです。
やり直したときには `phase` がもう `reveal` になっているので、2人目以降は何もせずに終わります。

## 5. 画面構成

すべての画面は `index.html` に入っていて、`showScreen('lobby')` のように切り替えます（1つだけ表示）。

| # | 画面 | id | 表示される条件 |
|---|---|---|---|
| 1 | トップ | `screen-top` | ルームに入っていないとき |
| 2 | ルーム作成 | `screen-create` | 「ルームを作成」を押したとき |
| 3 | ルーム参加 | `screen-join` | 「ルームに参加」を押したとき／招待リンクで開いたとき |
| 4 | 待機（ゲームモードの選択を含む） | `screen-lobby` | `status` が `lobby` |
| 5 | ゲーム | `screen-game` | `status` が `playing`、`phase` が `select` |
| 6 | ターン結果 | `screen-reveal` | `status` が `playing`、`phase` が `reveal` |
| 7 | 最終結果 | `screen-result` | `status` が `finished` |

待機画面（4）には「ゲームモードを選択」のカードがあります。中身は次の3つです。

| 部分 | ホスト | ほかの人 |
|---|---|---|
| モードの一覧（ハード／ノーマル／オリジナル） | タップして選べる | 見るだけ（押せない） |
| 選ばれているモードのルール（目標値・バースト・ターン数・キャラクター） | 表示される | 表示される（オリジナルのときは、ホストが決めた内容） |
| オリジナルのルール設定欄（入力欄） | オリジナルを選んでいるあいだだけ出る（上の「ルール」と入れ替わる） | 出ない |

また「最初の画面に戻る」ボタンがあり、押すとルームから退出してトップ画面（1）に戻ります（9章）。

ゲーム画面（5）は、自分の状況で中身が変わります。

| 自分の状況 | 表示 |
|---|---|
| まだ決定していない | 検索欄＋キャラクター一覧（そのゲームのルールで使える人だけ。50音順）＋下の決定欄 |
| 決定した | 「あなたの選択」と、ほかの人を待つ表示 |
| バーストした | 観戦の表示 |

画面上部のステータスバー（ターン・残りターン・モード・目標値・自分の合計点）は、スクロールしても常に見えます。

### 順位とポイントを表示する場所

「選ぶと何点になるか」が分からないことが、このゲームの大事な決まりです。
人気投票の順位と、それによって決まるポイントは、**結果が公開された後の画面にだけ**出します。

| 場所 | 順位・ポイント | 描いている関数（`views.js`） |
|---|---|---|
| キャラクター一覧・検索結果 | 出さない（名前だけ。並びも50音順） | `renderCharList` |
| 選択の確認欄 | 出さない（選ぶとバーストするかどうかも出さない） | `renderPickPanel` |
| 決定したあとの「あなたの選択」 | 出さない | `renderWaiting` |
| ターン結果画面 | **出す** | `renderRevealCards` |
| 最終結果画面の「ふりかえり」 | **出す** | `renderResult` |

同じ理由で、検索は名前とよみがなだけにしています（順位の数字で探せると、順位が分かってしまうため）。
画面を直すときは、上の3か所に順位やポイントが出ないようにしてください。

## 6. リアルタイム通信の方法

### 6-1. 全員が同じ場所を「購読」する

ルームに入ると、`rooms/{ルームID}` の変化を受け取り続けます（`watchRoom`）。
誰かがデータを書き換えると、全員の端末で `onRoomChange` が呼ばれ、画面が描き直されます。

```text
  誰かが書き込む ─▶ Firebase ─▶ 全員の onRoomChange(room) ─▶ render()
```

「メッセージを送り合う」のではなく、「同じデータを全員で見ている」と考えると分かりやすいです。

### 6-2. 1ターンの流れ（同時公開のしくみ）

```text
  Aさん                Firebase                 Bさん
   │ キャラを選んで決定                          │
   │── picks/…/A = 37（秘密）──▶│                │
   │── submitted/…/A = true ──▶│── Aが決定した ─▶│ 「A：決定」と表示
   │                           │                │ （誰を選んだかは届かない）
   │                           │                │ キャラを選んで決定
   │                           │◀── picks/…/B = 12（秘密）
   │◀── Bが決定した ───────────│◀── submitted/…/B = true
   │                           │                │
   │  全員が決定したと分かる      │                │  全員が決定したと分かる
   │── 全員の picks を読む ────▶│◀──── 全員の picks を読む
   │── 結果を計算して state を更新（トランザクション）
   │                           │   ※先に届いた1回だけが反映される
   │◀── state: phase = reveal ─│── state: phase = reveal ─▶│
   │  結果公開の画面へ           │                │  結果公開の画面へ
```

**相手の選択を見てから選べない理由**

セキュリティルール（`database.rules.json`）で、`picks` を次のように守っています。

- 書けるのは自分の欄に **1回だけ**（書いたら変更できない）
- そのラウンドの全員分を読めるのは、**自分の選択を書いた後**（またはバーストした人）だけ

つまり「先に自分の選択を確定させないと、ほかの人の選択は読めない」ので、後出しはできません。

**結果を計算するのは誰？**

「自分の選択を送り終えた人」の端末が、全員そろったことに気づいた時点で計算します。
たいていは最後に決定した人の端末です。ホストの端末に頼らないので、
ホストのスマホがスリープしていても結果公開まで進みます。

### 6-3. 切断の検知（プレゼンス）

`players/{uid}/online` で、つながっているかを表します。
Firebase の `onDisconnect` という機能で、「接続が切れたら、サーバー側で `false` と書く」よう予約しています。
ブラウザを閉じても、電波が切れても、サーバーが気づいて `false` にしてくれます。

## 8. 各ファイルの説明

呼び出しの関係は、上から下への一方向です。

```text
  main.js          入口。ボタンの処理、画面の切り替え
    ├─ views.js        画面を描く
    ├─ room.js         ルームとゲームの操作
    │    ├─ game-logic.js   ルールの計算
    │    └─ backend.js      通信係を選ぶ
    │          ├─ backend-firebase.js
    │          └─ backend-local.js
    ├─ util.js         小さな道具
    └─ config.js       設定値
```

### `js/config.js` ― 設定値

ゲームモードごとの設定（`GAME_MODES`：名前と、目標値・バーストする点数・ターン数・使えるキャラクターの順位）、
オリジナルで決められる値の上限（`ORIGINAL_LIMITS`）、人数 2〜5、プレイヤー名のデフォルト（霊夢）などを1か所にまとめています。
ルールの数字を変えたいときは、ここだけ書き換えます。

### `js/game-logic.js` ― ルールの計算

**このゲームで一番大事なファイルです。** 画面にも通信にも触らない、計算だけの関数が入っています。

| 関数 | すること |
|---|---|
| `listModes()` / `modeOf(状態)` | 画面に並べるモードの一覧／そのゲームのモード（名前など）を返す |
| `presetRules(モード)` | そのモードの、`config.js` に書いてあるルールを返す |
| `rulesOf(状態)` | そのゲームのルール（目標値・バーストする点数・ターン数・順位の範囲）を返す |
| `withMode(状態, モード)` | 待機中にモードを選んだ状態を返す。ルールもいっしょに状態に入る（ゲーム開始後は変えない） |
| `withOriginalRules(状態, ルール)` | 待機中にオリジナルのルールを決めた状態を返す（オリジナルが選ばれているときだけ） |
| `findRuleProblems(ルール, 一覧)` | ホストが入力したオリジナルのルールに問題がないか調べ、問題の説明を返す |
| `isValidRules(ルール)` | ルールとして使える形か（保存されているデータの確認に使う） |
| `isCharacterUsable(ルール, キャラ)` | そのキャラクターを、そのルールで使えるか（順位が範囲の中か） |
| `listUsableCharacters(ルール, 一覧)` | そのルールで使えるキャラクターだけを取り出す |
| `pointsFor(ルール, キャラ)` | 選んだときの加点（いまはどのモードも、順位そのまま） |
| `isBurst(ルール, 合計)` | その合計でバーストするか（合計が `burstScore` 以上ならバースト） |
| `createLobbyState(…)` / `createGameState(参加者, ゲーム番号, 待機中の状態)` | 待機中の状態／全員0点・1ターン目の状態を作る。モードとルールは開始時に固定される |
| `compatibilityOf(状態)` | そのゲームを、この画面のプログラムで正しく扱えるか（11-4） |
| `resolveTurn(状態, 全員の選択, キャラ表)` | 1ターン分の計算（下で説明） |
| `advance(状態)` | 次のターンへ進める。最後のターンの後、または全員バーストなら終了 |
| `judgeResult(状態)` | 勝者と順位を決める |
| `allActiveSubmitted(状態, 決定済みの印)` | バーストしていない人が全員決定したか |

目標値やターン数は、`150` や `5` と直接書かずに、必ず `rulesOf(状態)` から取り出しています。
こうしておくと、モードが増えても計算の部分を書き換えずに済みます（11章）。

`resolveTurn` の中身は、仕様の「重要なゲームロジック」と同じ順番です。

1. バーストしていない人の「有効な選択」を集める（未選択・使用禁止キャラ・そのルールで使えないキャラは除く）
2. キャラクターごとに、選んだ人数を数える
3. 1人ずつ結果を決める
   - 2人以上が選んだキャラ → **+0**、そのキャラを使用禁止リストに追加
   - それ以外 → **順位を加点**（`pointsFor`）
   - 合計がバーストする点数以上になったら **バースト**（`isBurst`。ハードは 150 がセーフ・151 でバースト、ノーマルは 50 がセーフ・51 でバースト）

> 状態の中では、バーストしたことを `out: true` という名前で持っています。
> この名前は Firebase のセキュリティルール（`database.rules.json`）とお試しモード（`backend-local.js`）が見ているので、変えていません。

結果の種類（`outcome`）は4つです。

| `outcome` | 意味 | 加点 |
|---|---|---|
| `ok` | ふつうに選んだ | 順位 |
| `duplicate` | ほかの人と重複した | 0 |
| `none` | 選ばなかった（ホストに締め切られた） | 0 |
| `invalid` | 使用禁止のキャラ、またはそのルールで使えないキャラだった（画面では選べないが、念のため） | 0 |

### `js/room.js` ― ルームとゲーム進行の操作

「ルームを作る」「参加する」「ゲームモードを選ぶ」「開始する」「決定する」「結果を計算する」「次へ進む」をまとめています。
それぞれ、**条件を確かめる → 通信係に頼む** という形です。

- 失敗したときは `GameError` を投げます。メッセージはそのまま画面に出せる日本語です。
  （例：「このルームはすでにゲームが始まっています。途中参加はできません。」）
- `setMode(roomId, room, モード)`：ホストが選んだモードと、そのルールを、ルームのデータに書き込みます。
  準備中のモードは `GameError` になり、ゲーム開始後は何も書き換えません。
- `setOriginalRules(roomId, room, ルール, キャラクター)`：ホストが決めたオリジナルのルールを書き込みます。
  入力に問題があるとき（`findRuleProblems`）は、書き込まずに `GameError` で知らせます。
- `startGame(roomId, room, オリジナルのルール, キャラクター)`：オリジナルのときは、ホストの設定欄にあるルールを
  受け取り、それを保存してから開始します（入力した直後に開始を押しても、画面どおりのルールで始まるように）。
- この3つは、ホスト以外の人が呼ぶと「この操作ができるのは、ホストだけです」という `GameError` になります。
- プレイヤー名が空欄のままのときは、`config.js` の `DEFAULT_PLAYER_NAME`（霊夢）を使います。
- `hostUidOf(room)`：いまホストとして操作できる人を返します。
  ルームを作った人が切断しているあいだは、オンラインの人のうち最初に入室した人が代わりになります。
- `resolveTurn` / `goNext` / `backToLobby`：4-4 のトランザクションで状態を書き換えます。

### `js/backend.js` と2つの通信係

`backend-firebase.js`（本番用）と `backend-local.js`（お試し用）は、**同じ名前・同じ動きの関数**を持っています。
`backend.js` が、`firebase-config.js` に設定があるかどうかを見て、どちらを使うか決めます。

| 関数 | すること |
|---|---|
| `init()` | 準備をして、自分のID(uid)を返す |
| `watchRoom(roomId, onChange)` | ルームの変化を受け取り続ける |
| `createRoom` / `writeMyPlayer` | ルームを作る／自分を名簿に書く・消す |
| `startPresence` / `stopPresence` | オンライン表示を始める／やめる |
| `updateState(roomId, updater)` | ゲーム状態を安全に書き換える（トランザクション） |
| `submitPick` | 自分の選択を送る（秘密の選択と、公開の「決定した印」を同時に書く） |
| `readPicks` / `readMyPick` | 全員の選択を読む／自分の選択を読む |

**通信係を分けている利点**

- Firebase を設定する前でも、1台のPCで全部の画面を試せる。
- ゲーム側のコード（`room.js` など）は、通信のしくみを知らなくてよい。
- 将来、別のサービスに乗り換えるときは、同じ関数を持つファイルをもう1つ作ればよい。

`backend-local.js` は、Firebase のセキュリティルールと同じ制限（開始後は参加できない、
決定前はほかの人の選択を読めない、など）をプログラムで再現しています。

### `js/views.js` ― 画面の描画

`app`（アプリの状態）を受け取って、`index.html` の中身を書き換えます。ボタンの処理は入っていません。

- 画面ごとに `renderLobby` / `renderGame` / `renderRevealCards` / `renderResult` があります。
- プレイヤー名など、利用者が入力した文字は必ず `escapeHtml()` を通してからHTMLに入れています。
  （名前に `<script>` のような文字を入れられても、画面が壊れないようにするため）
- 順位とポイントを出すのは、結果公開の後の画面だけです（5章の「順位とポイントを表示する場所」）。
- 目標値・バーストする点数・ターン数・使えるキャラクターは `rulesOf(状態)` から、モードの名前は `modeOf(状態)` から
  取り出して表示しています。「150」「50位」のような数字を、このファイルに直接は書いていません。
- 待機画面のルールの欄（`rulesRows`）と、「遊び方」のモードの説明（`describeRules`）は、ルールの数字から文章を作ります。
  そのため、オリジナルでどんなルールにしても、説明がそのルールに合います。
- 「遊び方」には、「このゲームには、相手の点数を奪う『スティール』はありません。◯回目（最後）の選択で、
  目標値にちょうど近くなるように注意してください」という注意書きを出します（`stealNote`。◯はターン数）。
- オリジナルの設定欄に値を入れるのは、設定欄を出し始めるときだけです（`renderModeCard`）。
  ルームのデータが届くたびに入れ直すと、ホストが入力している途中の文字が消えてしまうためです。

### `js/main.js` ― アプリの入口

1. **起動**：キャラクターデータを読み、通信係を準備する
2. **入室**：ルームを作る／参加する。リロード後は、保存しておいたルームIDで元のルームに戻る
3. **同期**：ルームのデータが変わるたびに `render()` で画面を描き直す
4. **操作**：ボタンが押されたら `room.js` の操作を呼ぶ
5. **自動処理**（`autoActions`）：全員が決定したら結果を計算する

`render()` は、状態を見てどの画面を出すかを決めるだけです。

```js
if (state.status === 'lobby')    → 待機画面
if (state.status === 'finished') → 最終結果画面
if (state.phase === 'reveal')    → ターン結果画面
それ以外                          → ゲーム画面
```

キャラクター一覧と結果公開のカードは、**新しいターンに入ったときだけ**作り直しています。
データが届くたびに作り直すと、検索中の文字やスクロール位置が消えたり、演出がやり直しになったりするためです。

### `js/util.js` ― 小さな道具

`$('id')`（要素を取り出す）、`showScreen`（画面切り替え）、`showToast`（下に出るメッセージ）、
`confirmDialog`（確認ダイアログ）、`normalizeText`（検索用に文字をそろえる）、
`parseWholeNumber`（入力された数字を整数にする。全角の数字も読める）などです。

キャラクター一覧のための関数もここにあります。

| 関数 | すること |
|---|---|
| `prepareCharacters(一覧)` | 検索用の文字列と並べ替え用のよみがなをつけ、**50音順**に並べた一覧を返す |
| `kanaRowOf(よみがな)` | 50音の「行」を返す（一覧の見出し「あ」「か」… に使う。濁点・カタカナも同じ行） |
| `compareKana(a, b)` | 2つのよみがなを50音順で比べる（ブラウザに備わっている日本語の辞書順を使う） |
| `searchCharacters(一覧, 検索語)` | 名前かよみがなに検索語を含むキャラクターを返す（順位では探せない） |

並べ替えに使う「よみ」は、漢字を含む名前なら `yomi`、かなだけの名前なら名前そのものです。
たとえば「射命丸 文」は「しゃめいまる あや」なので、さ行に入ります。

### `index.html` / `css/style.css`

- `index.html`：7つの画面の骨組みが全部入っています。中身（名前や点数）は `views.js` が入れます。
- `style.css`：スマホの縦画面を基本にしています。先頭の `:root` で色をまとめて管理しています。
  キャラクターの画像は使わず、陰陽玉のマークも図形（SVG）で描いています。

### `tools/convert_excel.py`

Excel（`.xlsx`）を読み、`data/characters.json` を作ります。
`.xlsx` は「XMLファイルをZIPでまとめたもの」なので、Python に最初から入っている機能だけで読めます。
読むのは「順位」と「名前」の列だけです。

### `database.rules.json`

Firebase のセキュリティルールです。各行に説明を書いてあります。守っていることは次の5つです。

1. ログイン（匿名認証）していない人は、何も読み書きできない
2. ルームの一覧は誰も見られない（ルームIDを知っている人だけが、そのルームを読める）
3. ゲーム開始後は、新しく参加できない
4. 選択は自分の分を1回だけ書ける
5. ほかの人の選択は、自分が決定した後でないと読めない

## 9. エラーや切断への対応

| 起きること | どうなるか | 関係する場所 |
|---|---|---|
| 通信が途中で切れた | 上に「通信が切れています」と出る。つながり直すと自動で続きから。ほかの人には「切断中」と表示される | `main.js` `watchConnection`、`backend-firebase.js` `startPresence` |
| ブラウザをリロードした | 保存しておいたルームIDで、同じゲームの同じ画面に戻る。決定済みの選択も読み直す | `main.js` `openFirstScreen` `restoreMyPick` |
| 存在しないルームIDを入力した | 「そのルームIDのルームは見つかりません」 | `room.js` `joinRoom` |
| すでに始まっているルームに入ろうとした | 「途中参加はできません」。ルールでも書き込みを拒否する | `room.js` `joinRoom`、`database.rules.json` |
| 満員のルームに入ろうとした | 「このルームは満員です」 | `room.js` `joinRoom` |
| プレイヤー名を空欄のまま進んだ | デフォルトの名前（霊夢）になる。同じ名前の人がいれば「霊夢2」のように番号がつく | `room.js` `createRoom` `joinRoom` |
| 準備中のモード（`available` が `false`）を選ぼうとした | 「◯◯ は準備中です」と出て、選択は変わらない | `room.js` `setMode` |
| ゲーム開始後にモードやルールを変えようとした | 待機画面にしか選ぶ場所がない。万一書き込もうとしても変わらない | `game-logic.js` `withMode` `withOriginalRules` |
| ホスト以外の人が、モードやオリジナルのルールを変えようとした | 一覧は押せず、設定欄も出ない。万一呼ばれても「この操作ができるのは、ホストだけです」になる | `views.js` `renderModeCard`、`room.js` `assertHost` |
| オリジナルで、矛盾した値を入力した（バーストする点数が目標値以下、順位の開始と終了が逆、数字でない など） | 設定欄の下に説明が出て、ルームには保存されない。そのまま「ゲーム開始」を押しても始まらない | `game-logic.js` `findRuleProblems`、`main.js` `onOriginalChange` `onStart` |
| オリジナルで、キャラクターが少なすぎる範囲にした | 「◯ターン遊ぶには◯人以上必要」と出る（重複で使用禁止になっても、最後のターンまで選べる人数が必要なため） | `game-logic.js` `neededCharacters` |
| オリジナルで、設定を入力した直後に「ゲーム開始」を押した | 確認ダイアログに出たルールが、そのまま保存されて始まる（保存が間に合わず、前のルールで始まることはない） | `room.js` `startGame` |
| キャラを選ばずに決定を押した | 「先に、一覧からキャラクターを選んでください」 | `main.js` `onDecide` |
| 使用禁止のキャラを選ぼうとした | 一覧で灰色になり、押しても選べない。万一送られても加点しない | `main.js` `onCharTap`、`game-logic.js` `resolveTurn` |
| そのルールで使えないキャラを選ぼうとした | 一覧にも検索結果にも出ない（検索すると「ノーマルでは選べません」と出る）。万一送られても加点しない | `views.js` `renderCharList`、`room.js` `submitPick`、`game-logic.js` `resolveTurn` |
| バーストした人が操作しようとした | キャラクター一覧が出ない（観戦表示）。ルールでも書き込みを拒否する | `views.js` `renderGame`、`database.rules.json` |
| 誰かがなかなか選ばない・戻ってこない | ホストは「未選択の人を待たずに結果を公開」で進められる（その人は +0） | `main.js` `onForce` |
| 待機画面で「最初の画面に戻る」を押した | ルームの名簿から自分を消して、トップ画面に戻る。ほかに人がいるときだけ確認を出す | `main.js` `onLeaveLobby` `leaveRoom`、`room.js` `leaveRoom` |
| 通信が切れているときに戻ろうとした | 画面は先にトップへ戻す。退出の通信は裏で行い、つながり直したときに送られる（通信を待つと、いつまでも戻れなくなるため） | `main.js` `leaveRoom` |
| ホストが待機画面から抜けた・切断した | 残っている人のうち最初に入室した人が次のホストになり、「あなたがホストになりました」と出る。ルームは消さない | `room.js` `hostUidOf`、`main.js` `noticeHostChange` |
| 古い画面のまま、新しいモードやルールのゲームに入った | 「ゲームが新しくなっています。再読み込みしてください」と出て止まる（違うルールで計算しないため。11-4） | `main.js` `onRoomChange`、`game-logic.js` `compatibilityOf` |
| ホストが古い画面のままゲームを開始した | 新しい画面の人には「古いバージョンの画面から始められたため、続けられません」と出て、ルームから出る（11-4） | `main.js` `onRoomChange`、`game-logic.js` `compatibilityOf` |
| 2人が同時に同じ操作をした | トランザクションにより、1回だけ反映される | `room.js`、4-4 |

## 10. 機能を足すときのヒント

| やりたいこと | 手を入れる場所 |
|---|---|
| 制限時間をつける | `state` に締め切り時刻を入れ、`main.js` の `autoActions` で時間切れなら `resolveTurn` を呼ぶ |

## 11. ゲームモード

### 11-1. しくみ

ルールはモードごとに別々に持っています。設定は `js/config.js` の `GAME_MODES` にまとめてあります。
「150点のゲーム」を前提にして一部だけ変える、という作りにはしていません。どのモードも、自分のルールを全部持っています。

```js
export const GAME_MODES = {
  hard:     { name: 'ハード',     description: '150点を目指す',      available: true,
              targetScore: 150, burstScore: 151, maxTurns: 5, minRank: 1, maxRank: null },
  normal:   { name: 'ノーマル',   description: '50点を目指す',       available: true,
              targetScore: 50,  burstScore: 51,  maxTurns: 5, minRank: 1, maxRank: 50 },
  original: { name: 'オリジナル', description: '自分でルールを設定', available: true, custom: true,
              targetScore: 100, burstScore: 101, maxTurns: 5, minRank: 1, maxRank: null },
};
```

| 項目 | 意味 |
|---|---|
| `name` / `description` | 画面に表示する名前と、待機画面に出すひとことの説明 |
| `available` | `true` なら選べる。`false` にすると「準備中」と表示され、選べない |
| `custom` | `true` のモードは、ホストが待機画面でルールを決められる。下の5つは「最初に入っている値」になる |
| `targetScore` | 目標値 |
| `burstScore` | バーストする点数。合計がこの点数**以上**になったらバースト |
| `maxTurns` | ターン数 |
| `minRank` / `maxRank` | 使えるキャラクターの順位の範囲。`maxRank` が `null` なら「最後の順位まで」 |

いまのモードは次のとおりです。

| モード | 使えるキャラクター | 目標値 | バースト | ターン |
|---|---|---:|---:|---:|
| ハード | 全キャラクター（225人） | 150 | 151以上 | 5 |
| ノーマル | 人気投票 1〜50位（50人） | 50 | 51以上 | 5 |
| オリジナル | ホストが決める | ホストが決める | ホストが決める | ホストが決める |

**目標値とバーストする点数は、別々の数字として持っています。**
判定は「目標値を超えたら」ではなく、「合計が `burstScore` 以上なら」です（`game-logic.js` の `isBurst`）。

```js
export function isBurst(rules, total) {
  return total >= rules.burstScore;
}
```

**ルールは、設定 → 状態 → 計算・画面 の順に流れます。**

```text
 ゲームモードの設定（config.js の GAME_MODES）
        │  ホストがモードを選ぶ（withMode）／オリジナルのルールを決める（withOriginalRules）
        ▼
 ゲームの状態（rooms/{ルームID}/state の mode と rules）   ← ルームに1つだけ。全員が同じものを見る
        │  rulesOf(状態)
        ▼
 ルールの計算（game-logic.js）          画面（views.js）
   isCharacterUsable / isBurst            一覧・ステータスバー・待機画面のルール・「遊び方」
   resolveTurn / judgeResult …
```

計算も画面も、`config.js` の数字を直接は見ません。必ず `rulesOf(状態)` から読みます。
そのため、次のことが成り立ちます。

- ハード・ノーマル・オリジナルで、計算や画面のプログラムは共通（モードごとに書き分けていない）。
- モードを増やしたり数字を変えたりしても、計算と画面は書き換えなくてよい。
- ゲームが始まったあとで `config.js` を書き換えて公開し直しても、進行中のゲームのルールは変わらない
  （そのゲームのルールは、開始したときに状態に入っているため）。

ハードの `maxRank` を `225` ではなく `null`（最後の順位まで）にしているのは、
人気投票のデータを差し替えて人数が変わっても、書き直さずに済むようにするためです。
オリジナルで決められる順位の範囲（1位〜最後の順位）も、データから求めています（`rankSpanOf`）。

**使えるキャラクターの範囲は、4か所で同じ関数（`isCharacterUsable`）を使って確かめています。**

| 場所 | すること |
|---|---|
| 一覧と検索（`views.js` `renderCharList`） | 使えるキャラクターだけを表示する。並びは50音順のまま |
| 決定するとき（`room.js` `submitPick`） | 使えないキャラクターは送らずに、エラーにする |
| 結果の計算（`game-logic.js` `resolveTurn`） | 万一送られてきても、無効（+0）として扱う |
| 「遊び方」と待機画面の説明（`views.js`） | 「人気投票 1〜50 位」のように、ルールから文章を作る |

「順位で絞ること」と「画面に50音順で並べること」は別の処理です。
一覧は最初に全員を50音順に並べてあり（`prepareCharacters`）、そこから使える人だけを取り出すので、順番は50音順のままです。

### 11-2. モードとルールが全員に共有されるまで

```text
 待機画面でホストがモードをタップ
        │  room.js  setMode
        ▼
 rooms/{ルームID}/state/mode  = "normal"
 rooms/{ルームID}/state/rules = { targetScore: 50, burstScore: 51, … }   ← ルームのデータに1つだけ保存
        │  全員がこのデータを見ている（6章）
        ▼
 全員の待機画面に「モード：ノーマル」と、そのルールが表示される
        │  ホストが「ゲーム開始」
        ▼
 ゲームの状態に mode と rules が入ったまま開始（ここで固定）
        │
        ▼
 ゲーム中・結果画面の表示と計算は、すべて rulesOf(状態) を使う
```

- モードとルールは**ルームに1つ**だけ保存されるので、プレイヤーごとに違うルールになることはありません。
- 変更できるのは待機中（`status` が `lobby`）だけです。`withMode` と `withOriginalRules` が、ゲーム開始後の変更を受けつけません。
- 選べるのはホストだけです。ほかの人の画面では、一覧が押せない状態になっています（`room.js` でも確かめています）。
- 「もう一度」で待機画面に戻ったときは、前回のモードとルールが選ばれたままになります。
- モードやルールの記録がない古いルーム（前のバージョンで作られた、待機中のルーム）は、ハードとして扱います。

### 11-3. オリジナル

オリジナルは、ホストが待機画面でルールを決めるモードです（`config.js` で `custom: true` のモード）。

```text
 ホストが設定欄に入力する（目標値・バースト・ターン数・順位の開始と終了）
        │  1文字ごと: main.js onOriginalInput
        │     ・キャラクターの人数と、入力の問題点を表示する（findRuleProblems）
        │     ・目標値を変えたら、バーストを自動で「目標値 + 1」にする
        │  入力を終えたとき: main.js onOriginalChange
        │     ・問題がなければ room.js setOriginalRules で保存する
        ▼
 rooms/{ルームID}/state/rules と state/original に保存
        │
        ▼
 参加者の待機画面に「オリジナルのルール（ホストが設定）」として表示される
        │  ホストが「ゲーム開始」
        ▼
 「このルールで開始しますか？」の確認 → 開始
```

- `state.rules` は「いま選ばれているモードのルール」、`state.original` は「ホストが決めたオリジナルのルール」です。
  2つに分けているのは、いったんハードやノーマルに変えても、オリジナルに戻したときに、決めた内容が残るようにするためです。
- 入力のチェック（`findRuleProblems`）で確かめていること
  - 目標値は 1〜9999、ターン数は 1〜20 の整数（上限は `config.js` の `ORIGINAL_LIMITS`）
  - バーストする点数は、目標値より大きい（目標値ちょうどでバーストする、という矛盾を防ぐ）
  - 順位は、データにある範囲（1位〜最後の順位）の中で、開始が終了以下
  - その範囲のキャラクターが、最後のターンまで全員が選べるだけいる（`neededCharacters`）。
    重複すると使用禁止になり、1ターンに最大2人ずつ減るため、5ターンなら9人以上が必要
- 同率順位があるので、人数は「終了 − 開始 + 1」ではなく、実際に数えています（設定欄に「この範囲のキャラクター：◯人」と出ます）。
- バーストする点数を「目標値 + 1」より大きくすると、目標値を超えてもバーストしない点数ができます。
  そのときも勝敗は「目標値にいちばん近い人」です（`judgeResult` は、目標値との差を0以上の数で比べます）。
  ハードとノーマルは「バースト ＝ 目標値 + 1」なので、これまでどおり「目標値を超えずに、いちばん近い人」になります。

### 11-4. バージョンがちがう画面への対応

ゲームを更新して公開し直したあと、古い画面を開いたままの人がいると、人によって違うルールで計算してしまうおそれがあります。
それを防ぐため、ルームのデータが届くたびに `compatibilityOf(状態)` で確かめています（`main.js` の `onRoomChange`）。

| 結果 | どんなとき | 画面 |
|---|---|---|
| `ok` | ふつうのとき（待機中は、モードを選び直せばよいので、いつも `ok`） | そのまま進む |
| `reload` | ゲーム中の状態に、この画面が知らないモードや、知らないルールの項目が入っている（この画面のほうが古い） | 「ゲームが新しくなっています。ページを再読み込みしてください」と出て止まる |
| `broken` | ゲーム中の状態に、ルールが入っていない（もっと前のバージョンの画面から始められた） | 「古いバージョンの画面から始められたため、続けられません」と出て、ルームから出る |

状態に入っている `difficulty: "reload"` は、**前のバージョンの画面を止めるための印**です。
このゲームは以前、モードを `difficulty`（`hard` / `lunatic` など）で表していました。前のバージョンの画面は、
知らない難易度のゲームを見ると「再読み込みしてください」と出て止まるので、わざと知らない名前を入れてあります
（`game-logic.js` の `OLD_SCREEN_STOPPER`）。いまのコードは、この項目を読みません。

### 11-5. モードを追加するとき・ルールの種類を増やすとき

**目標値・バーストする点数・ターン数・使えるキャラクターを変えるだけの場合**は、`config.js` に1つ足すだけです。

```js
  easy: { name: 'イージー', description: '100点を目指す', available: true,
          targetScore: 100, burstScore: 101, maxTurns: 3, minRank: 1, maxRank: 100 },
```

待機画面で選べるようになり、キャラクター一覧と検索、ステータスバー（TURN 1 / 3、目標 100 点）、
待機画面のルールの欄、「遊び方」の説明、バーストの判定、終了するターン、最終結果の「100との差」、
トップ画面の「イージー：100点を目指す」が、すべてこの設定に合わせて変わります。
ほかのモードの設定とコードは、そのままです。
（この動きは `tests/` の「設定を1つ足すだけで…」のテストでも確認しています）

**ルールの種類そのものを増やしたい場合**（特殊ルール、得点計算の変更、オリジナルの設定項目の追加など）は、
次の表の場所を直します。「ルールによって違うところ」は、`rules` を受け取る小さな関数に分けてあるので、直す場所は1か所で済みます。

| 変えたいもの | 直す場所（`game-logic.js`） | いまの決まり |
|---|---|---|
| 使えるキャラクターの範囲 | `isCharacterUsable` | 順位が `minRank`〜`maxRank` の中 |
| 得点計算 | `pointsFor` | 順位がそのまま点数 |
| バーストする条件 | `isBurst` | 合計が `burstScore` 以上ならバースト |
| 重複したときの扱い | `resolveTurn` の「重複」の部分 | 全員 +0、そのキャラは以降使用禁止 |
| 勝敗判定 | `judgeResult` | バーストしていない人のうち、`targetScore` との差が最小の人 |
| ターン数 | `isLastReveal` | `maxTurns` ターンで終了 |

手順は、どれも同じです。

1. `config.js` で、モードの設定に項目を足す
2. `game-logic.js` の `RULE_KEYS` に、その項目の名前を足す（ルールの項目として扱われ、状態に保存されるようになる）
3. 上の表の関数で、その項目を見て処理を分ける
4. `isValidRules`（と、オリジナルで決められるようにするなら `findRuleProblems`）に、その項目のチェックを足す

たとえば「重複しても使用禁止にしないモード」を作るなら、次のようになります。

```js
// 1. config.js … 設定に項目を足す（書いていないモードは、これまでどおり使用禁止にする）
  easy: { name: 'イージー', description: '重複しても禁止にならない', available: true,
          targetScore: 150, burstScore: 151, maxTurns: 5, minRank: 1, maxRank: null, keepDuplicates: true },

// 2. game-logic.js … ルールの項目に足す
export const RULE_KEYS = ['targetScore', 'burstScore', 'maxTurns', 'minRank', 'maxRank', 'keepDuplicates'];

// 3. game-logic.js の resolveTurn … 使用禁止にするところで、その項目を見る
  if (!rules.keepDuplicates) banned[banKey(character.id)] = state.turn;
```

「順位の半分（切り上げ）を点数にするモード」なら、3. で `pointsFor` を直します。

```js
export function pointsFor(rules, character) {
  return rules.halfPoints ? Math.ceil(character.rank / 2) : character.rank;
}
```

どちらの例でも、項目を書いていないモード（ハード・ノーマル）の動きは変わりません。
`RULE_KEYS` に項目を足すと、その項目を知らない古い画面は 11-4 のしくみで「再読み込みしてください」と出て止まるので、
新しいルールを知らない画面が、違う計算をしてしまうこともありません。

**オリジナルの設定項目を増やす場合**は、上の 1〜4 に加えて、次の3か所に入力欄を足します。

| 場所 | すること |
|---|---|
| `index.html` の `#original-form` | 入力欄を1つ足す |
| `views.js` の `ORIGINAL_INPUTS` | 「ルールの項目名 → 入力欄の id」を1行足す（値を入れる・読むのは、この表をもとに自動で行われる） |
| `views.js` の `rulesRows` | 待機画面のルールの欄と、開始前の確認に出す行を足す |

ルールを足したら、`tests/game-logic.test.js` にテストも足してください
（「ノーマルのテスト」「オリジナルのテスト」が、書き方の見本になります）。
